# DSV4 RL-Kernel / verl integration

This opt-in entrypoint runs verl's synchronous v1 trainer with its native GRPO
reward, advantage and PPO policy loss. RLK supplies the native MCore operator
bindings, selected FP32 logprob provider, original packed checkpoint loading and
checked synchronization to a live standalone vLLM PP2 replica.

It consumes actual forward logits at the provider boundary, following the
integration pattern in [Vime #424](https://github.com/vllm-project/vime/pull/424).
It does not replace the trainer with the four-layer diagnostic loss or an
independent training engine.

The existing image also needs its matching Bridge/AITER/Torch/ROCm dependencies.
Record the actual installed commits, local patches, package versions and image
digest before accepting a result. The original four-layer checkpoint and scales
must be identical on both sides. Packed FP4/FP8 bases remain frozen; the native
optimizer updates the supported nonquantized parameters and retains input VJPs
through the packed experts. This is not full-parameter quantized-weight training.

## Four-card topology

- Actor: PP2, DP1, TP1, EP1, CP1, two GPUs.
- Rollout: a separate native vLLM PP2 replica, two other GPUs.
- Both engines own original checkpoint layers `0–2 / 3`.
- Eager mode, no LoRA, MTP, reference/KL, critic, sleep, prefix caching or resume.
- Unit temperature, full vocabulary scores, no top-k/top-p truncation.
- GRPO uses at least two completions per prompt. The mini-batch setting counts
  prompts; equal `data.train_batch_size` and `actor.ppo_mini_batch_size` with one
  PPO epoch yield one real optimizer update per global step.

## Entry

Install the community verl branch and RLK #711 in the isolated runtime, keeping
the previously measured MCore/vLLM dependencies. Do not install a second upstream
verl over this fork. Run only after the selected four GPUs are actually free;
restrict device visibility and Ray GPU resources before launching this command.

```bash
python -m verl.experimental.rl_kernel.main_ppo \
  actor_rollout_ref.model.path=/models/4l \
  data.train_files=/data/train.parquet \
  data.val_files=/data/val.parquet \
  data.train_batch_size=2 \
  actor_rollout_ref.actor.ppo_mini_batch_size=2 \
  actor_rollout_ref.rollout.n=2 \
  trainer.total_training_steps=3 \
  trainer.default_local_dir=/outputs/checkpoints \
  rlk.sync_dir=/outputs/policy-sync
```

These are explicit mount paths, not bundled model/data assets. Use a real
supported rule-reward dataset, or its documented custom reward implementation.
Check that group rewards and advantages actually differ; zero advantages and
unchanged weights cannot qualify as three effective training updates.

## What the adapter records

- `parity.jsonl`: actor old-logprob versus actual rollout scores from the native
  TransferQueue batch, compared as finite FP32 bits on response positions.
- `training-batch-step{1,2,3}.json`: actual native reward/return/advantage summaries.
- `actor-rank-*-identity.json`: live actor PIDs, device identities and layer ownership.
- `actor-rank-*-v{1,2,3}.json`: native optimizer versions, finite/nonzero gradient
  evidence and parameter changes on both actor stages.
- `sync-v{0,1,2,3}.json`: complete original-tensor readback on both live rollout
  stages. Version zero verifies the shared initial checkpoint; it is not an update.
- `post-update-v{1,2,3}.json`: new tokens generated by the live updated rollout
  and scored by the same live actor. This also verifies the final update.

Sync closes admissions and clears caches before export. A missing shard, stale
version, changed worker PID, incomplete readback, nonfinite score or bit mismatch
fails the run. Ordinary non-RLK entrypoints and registries are unchanged.

## Strict acceptance

Use the source-locked image builder, four-device launcher, checkpoint inventory
and independent `verify_grpo.py` from RLK #711. The launcher executes this formal
entrypoint in a new container with model, data, cache and output mounts only.
`copy_task.py` supplies six explicit text-copy instructions and a reference-based
normalized Levenshtein reward for functional integration; it is not a benchmark
or evidence of learning gains. Other supported real rule-reward datasets remain
configurable through the normal trainer.

The audit keeps fixed sequences across versions and also generates fresh A/B/C
responses after each update. It observes actual B1/B2 AB/BA/AC/CA and repeats on
both native engines, including real scheduler ordering and actor forward inputs.
The raw FP32 words are saved before any comparison can fail. The native PPO loss,
PP transfers, effective gradients, changed parameters and optimizer/moment state
are recorded at every step. Only the final actor PP stage evaluates the loss.

RLK binds compressor FP32 projection on both native MCore and AMD vLLM, including
the latter's fused main/indexer GEMM. Shape-dependent production GEMM accumulation
otherwise differed on natural-language tokens despite matching operands and
original weights. Original BF16 compressor parameters, packed FP4/FP8 bases and
scales retain their dtypes; only the three routing-index tables use the existing
lossless int64-to-int32 native ABI. Quantized bases remain frozen.

The native 1F1B schedule declares its actual microbatch count to RLK's canonical
backward session before registration. Parameter VJPs are emitted only after all
uses arrive; missing, duplicate or extra submissions fail. The optimizer and
scheduler state are retained across versions 0, 1, 2 and 3.

Machine results and limitations belong to the report linked from
[RLK #711](https://github.com/RL-Align/RL-Kernel/pull/711). Earlier diagnostic-loss
results do not qualify this full trainer. Acceptance requires one uninterrupted
three-update job, new generation after update three, complete evidence verification
and a clean process exit. Do not infer DP2, a full model, multiple nodes, independent
training-trajectory determinism or performance gains from this recipe.

## Experimental multi-node PP2

The `dsv4-rocm-multinode` change requires the updated RL-Kernel #711. It adds
explicit per-role Ray node IPs, shared-storage/source/input preflight and checked
actual node/rank/PCI placement. Each role still has exactly two PP ranks: either
two GPUs on one host or one GPU on each of two hosts. TP/EP/CP/DP remain 1 and the
model remains four layers with original ownership `0–2 / 3`. Full-model and
additional parallel axes are still rejected/not supported by this recipe.

Use `rlk.multinode=true`, `rlk.actor_node_ips=[...]` and
`actor_rollout_ref.rollout.rlk_node_ips=[...]`, with matching `nnodes` and
`n_gpus_per_node` (1x2 or 2x1) for each role. A shared filesystem at `rlk.sync_dir`
is required; local directories with the same name are insufficient. Preflight
hashes the checkpoint and input files on every selected node before GPU worker
allocation. All nodes must run identical, clean source commits and dependency
versions. The pinned vLLM's native multi-node `mp` executor and headless follower
are reused; no new transport or modified upstream executor is introduced.

Use RLK's `examples/operators/dsv4_4l/run_cluster_grpo.py` to attach to an existing
allocated Ray cluster. The complete per-node bootstrap, two supported placements,
submission and verifier commands are in
[the AMD handoff guide](https://github.com/RL-Align/RL-Kernel/blob/vensen/dsv4-4l-pp2-dp2-20261116/docs/usage/dsv4-rocm-amd-handoff.md).
After #711 merges, use the same path on `dsv4-rocm` and pin its commit.

The existing versioned export/load/readback protocol now uses node-qualified
process identities; equal PIDs on separate nodes are allowed, restarts are not.
Actual actor and rollout PCI assignments must be disjoint on each node.
Failures leave the job failed; no local or stale-policy fallback is enabled.
The independent verifier checks placement against raw worker evidence.

Validation for this extension is CPU-only. AMD multi-node model execution,
RCCL behavior, numerical parity and performance are pending hardware testing.
The historical single-node failure and GPU setup errors remain unresolved.
